A vector database is basically a database made to store and search vector embeddings efficiently. AI models convert text, images, or other data into these long lists of numbers called embeddings that capture meaning and context. Things that are semantically similar end up close to each other in that high-dimensional space. Normal databases are built for exact matches or keyword search, so they struggle with this kind of similarity search at scale. Vector databases add proper indexing (usually something like HNSW), metadata filtering, durability, and the usual database features on top of the pure search algorithms.

For a real problem, let’s say we’re building the retrieval part for an internal company RAG system. The knowledge base has product docs, support tickets, engineering notes, policies, meeting notes after chunking we could be looking at 50 to 150 million vectors. People will search through a chat interface or search bar. Almost every query will have filters: department, document type, date range, access level (so multi-tenancy matters). We also need hybrid search because people often type exact ticket numbers, error codes, or product names. Latency should stay decent, ideally under 80 ms for the retrieval step. The team can handle basic Docker or Kubernetes but doesn’t want something heavy and distributed to maintain, and self-hosting needs to be possible for compliance.

For this I’d pick Qdrant.

The main reason is filtering. Most vector databases look fine when you just do pure similarity search. The moment you start adding multiple filters on almost every query, some of them slow down or the recall drops. Qdrant’s payload filtering is actually pretty good for this. You can attach arbitrary metadata to each vector and filter on it efficiently during search. That’s important here because in an internal knowledge base almost every search will be filtered.

Hybrid search is also built-in. You can store dense vectors and sparse vectors in the same collection and combine them in one query. That means we get semantic search plus keyword matching without running a separate search system and merging results ourselves, which is messy.

Scale-wise, 50–150 million is comfortable territory for Qdrant. It uses HNSW, which works well at this size, and they have quantization options if memory starts becoming expensive. Latency stays reasonable even with filters from what I’ve seen. On the ops side it’s practical — open source, relatively easy to run as a single binary or in Docker/K8s, and they have a managed cloud if we later decide we don’t want to operate it. Not as zero-ops as Pinecone, but also not as heavy as full Milvus. For a team with some DevOps capacity but not a big platform team, it sits in a good middle. Cost is also better than pure managed options once you grow past a few tens of millions of vectors, especially if we self-host.

If the team had almost no DevOps bandwidth and just wanted something that works immediately, I’d probably go with Pinecone. It’s very easy, the multi-tenancy is solid, and you don’t have to think about infrastructure. But for this problem, since cost and self-hosting matter, Qdrant makes more sense. Weaviate is also strong, especially on hybrid search and schema flexibility — it’s a close second. I might choose it if the data model was more complex. Milvus is overkill here; it’s built for much larger scale. pgvector would be fine if we were already deep in Postgres and the collection stayed smaller. Chroma is only really for prototyping.

In practice I’d start small. Take a few hundred thousand real chunks, generate embeddings with the same model we’ll use in production, load them with realistic metadata, apply the exact filters the product team expects, and measure latency and whether the results actually make sense. I’d also check insert and update speed because new tickets and docs keep coming. Only after that would I scale to the full dataset. And honestly, the vector database is important but it’s not the biggest factor. Chunking strategy and the quality of the embedding model usually matter more for the final answer quality.
